# Fileward

Fileward — лёгкий локальный демон автоматизации для Linux.

Он следит за событиями файловой системы, проверяет их по правилам и выполняет действия `log`, `move`, `copy`, `archive` и `exec`. Поддерживаются условия, приоритеты, фильтры, политики конфликтов и шаблоны путей назначения.

Версия 1.0 объединяет наблюдение через `inotify`, ограниченный планировщик, модульные обработчики действий и структурированный аудит. Сервис работает без сетевого сервера и внешней базы данных.

## Структура проекта

- `src/app/` — CLI и управление демоном
- `src/core/` — конфигурация, правила, glob
- `src/actions/` — файловые действия, exec, шаблоны
- `src/watcher/` — inotify
- `src/runtime/` — очередь, готовность файлов, пул потоков
- `src/observability/` — диагностика, JSONL, история/статистика
- `include/fileward/` — публичные интерфейсы модулей
- `tests/unit/`, `tests/integration/` — unit и интеграционные проверки
- `documentation/` — архитектура, схема событий и каталог ошибок
- `integrations/` — шаблоны Wazuh и адаптер входных данных Shuffle
- `third_party/jsmn/` — закреплённый MIT-парсер JSON для query-команд
- `systemd/`, `.github/workflows/ci.yml` — сервисы и CI
- `example.conf` — единственный общий пример; `fileward.conf` — локальная копия

## Идея

```text
Триггеры → Правила → Действия
```

То есть:

```text
Событие произошло -> правило совпало -> действие выполнено
```

Примеры:

```text
PDF появился в ~/Downloads       -> переместить в ~/Documents/PDF
ZIP появился в ~/Downloads       -> переместить в ~/Archives
TXT появился в ~/Downloads       -> записать сообщение в лог
```

## Быстрый запуск за три команды

Из корня клонированного репозитория на Debian/Ubuntu с работающим пользовательским systemd:

```bash
sudo apt-get install -y build-essential meson ninja-build pkg-config zlib1g-dev python3
make install-user
make health-user
```

`make install-user` собирает программу, устанавливает её и запускает сервис без `sudo`.
При первой установке создаётся `~/Downloads/Fileward/inbox` и правило, которое только
журналирует новые файлы. Проверьте работу командой `touch ~/Downloads/Fileward/inbox/hello.txt`
и посмотрите журнал: `make logs-user`. Если зависимости уже установлены, нужны только
последние две команды.

Правила сервиса хранятся в `~/.config/fileward/fileward.conf`; отредактируйте их и
выполните `make reload-user`. Установщик сохраняет существующую конфигурацию.
Чтобы при первой установке использовать свою локальную конфигурацию, выполните
`make install-user CONFIG=fileward.conf`. [Подробности установки и управления](documentation/deployment.md).

## Текущий статус

Текущая версия — `v1.0.0`, ветка `v1.0-engine`. Все пункты roadmap v1.0 реализованы:

- watcher, планировщик, обработчики и хранилище состояния имеют отдельные интерфейсы;
- парсер и исполнитель используют общий реестр модульных обработчиков;
- `health` возвращает живое состояние очереди, потоков, наблюдения и аудита в JSON;
- `reload` подтверждает применение конфигурации и сохраняет прежние правила при ошибке;
- user/system services используют уведомление готовности, watchdog и восстановление после сбоя;
- установка и обновление выполняются одной командой с сохранением конфигурации и журналов.

Сохраняются правила и действия v0.6–v0.8, JSONL, параллельное исполнение,
ожидание готовности файлов и шаблоны интеграций v0.9. Восстановление процесса
через systemd не переигрывает пропущенные события или незавершённые задания.

## Сборка

Нужны:

- Linux (`inotify`, `renameat2`), glibc >= 2.34 (`posix_spawn` с closefrom); для service-режима — systemd;
- C-компилятор;
- Meson;
- Ninja, Make, pkg-config и заголовки zlib;
- Python 3 для интеграционной проверки действий (`make check`).

На Ubuntu/Debian:

```bash
sudo apt-get update
sudo apt-get install -y build-essential meson ninja-build pkg-config zlib1g-dev python3
```

Сборка:

```bash
meson setup build
meson compile -C build
```

Подготовка примера и справка (команды выполняются из корня репозитория):

```bash
mkdir -p ~/Downloads/FilewardLab/{inbox,staging}
test -e fileward.conf || cp example.conf fileward.conf
./build/fileward help
```

В репозитории один общий пример — `example.conf`; `fileward.conf` — его локальная копия, исключённая из Git. Пример использует отдельную песочницу `~/Downloads/FilewardLab`: сначала копирует входящие файлы, создаёт gzip-копии TXT, затем перемещает оригиналы по правилам. `exec` отключён по умолчанию. Файлы готовят в `staging` и переносят в `inbox` во время работы watcher. Сначала можно посмотреть предполагаемые действия через `--dry-run`. Без конфига программа только выводит события. Для остановки обычного запуска нажмите `Ctrl+C`.

Запуск:

```bash
./build/fileward run ~/Downloads
```

или через `run` target:

```bash
make run
```

Запуск с конфигурационным файлом:

```bash
./build/fileward run --config fileward.conf
```

Запуск в режиме dry-run:

```bash
./build/fileward run --dry-run --config fileward.conf
```

или без конфига:

```bash
./build/fileward run --dry-run ~/Downloads
```

Проверка синтаксиса конфигурации без запуска watcher и выполнения действий:

```bash
./build/fileward validate --config fileward.conf
```

`validate` не требует существования каталога `watch` и не проверяет доступность путей или возможность перемещения. Используется тот же парсер, что при запуске и reload; ошибочный конфиг возвращает код `2`.

Проверка пути и правил (файл должен существовать внутри `watch`; действия не выполняются):

```bash
./build/fileward test --config fileward.conf ~/Downloads/FilewardLab/inbox/report.pdf
```

Объяснение совпадений:

```bash
./build/fileward explain --config fileward.conf --event moved_to ~/Downloads/FilewardLab/inbox/report.pdf
```

Перезагрузка конфигурации через SIGHUP:

```bash
kill -HUP 12345
```

Замените `12345` на PID своего процесса. Для фонового запуска удобнее команда `reload`, для systemd — `systemctl reload` (примеры ниже).

Если `fileward` запущен с `--config fileward.conf`, он перечитает конфиг и применит новые правила без перезапуска.
При ошибке в новом конфиге старые правила продолжают работать. Если поменялся каталог `watch`, нужен перезапуск сервиса.

Запись логов в файл при обычном или фоновом запуске:

```bash
./build/fileward run --config fileward.conf --log-file ~/fileward.log
```

Каталог для наблюдения можно передать после опций: он заменит `watch` из конфига, в том числе при reload. Относительные пути считаются от рабочей папки запуска, которую демон сохраняет. Для systemd-конфигов используйте абсолютные пути или `~/...`. Родительские каталоги для log/state/pid-файлов должны существовать; храните эти файлы вне наблюдаемого дерева.

Основные команды:

| Команда | Назначение |
| --- | --- |
| `help`, `--help` | Справка |
| `run` | Наблюдение в foreground; `run --daemon` включает фоновый запуск |
| `start` | Запуск в фоне с подтверждением запуска watcher-а |
| `stop` | Отправка SIGTERM и ожидание остановки до 5 секунд |
| `status` | Печать `running` или `stopped` по pidfile |
| `reload` | Отправка SIGHUP; результат перечитывания виден в логе |
| `validate` | Проверка синтаксиса конфига и числа включённых/отключённых правил |
| `test` | Проверка существующего пути и правил для события `created` |
| `explain` | Объяснение правил для выбранного `--event`, включая удалённый файл |

`run/start`: `--config`, `--dry-run`, `--pidfile`, `--log-file`, `--state-file`; `run` также принимает `--daemon`. `stop/status/reload` принимают `--pidfile`. `validate` принимает только `--config <file>`. `validate/test/explain` не запускают watcher и не изменяют файлы.

Коды завершения: `0` — успешное выполнение, `1` — ошибка аргументов/пути вне `watch`, `2` — ошибка конфига, `3` — ошибка выполнения. `status` возвращает `0` и для `stopped`: проверяйте его текстовый вывод.

## Работа с Makefile

Для повседневной разработки удобнее использовать `Makefile`. `make help` показывает все цели; `make clean` удаляет каталог сборки.

Собрать проект:

```bash
make build
```

Собрать проект и запустить проверки:

```bash
make check
```

`make check` собирает проект, проверяет CLI, запускает unit-тесты парсера, правил, glob, действий, состояния и отказов аудита; сценарии исполнения, управления, установки и локальную проверку интеграционных шаблонов. Unit-тесты отдельно: `meson test -C build --print-errorlogs`.

Проверки reload, log-file, блокировки pidfile, start/stop и state-file:

```bash
bash tests/integration/service-smoke.sh
bash tests/integration/daemon-smoke.sh
bash tests/integration/rules-smoke.sh
bash tests/integration/rules-v07-smoke.sh
python3 tests/integration/actions-smoke.py
python3 tests/integration/observability-smoke.py
python3 tests/integration/integrations-test.py
```

Эти проверки также запускаются в GitHub Actions на Ubuntu при push и pull request. Для проверки настоящего systemd на машине с пользовательским manager выполните `make check-systemd`. Используется отдельный временный сервис; сценарий проверяет reload, восстановление после SIGKILL и срабатывание watchdog. Подробнее: [проверки](documentation/testing.md).

Установить бинарь и user-service:

```bash
make install-user
```

Перезапустить user-service после изменений:

```bash
make restart-user
```

Посмотреть статус:

```bash
make status-user
```

Смотреть логи:

```bash
make logs-user
```

Удалить user-service и установленный бинарь:

```bash
make uninstall-user
```

`install-user` ставит бинарь в `~/.local/bin/fileward`, unit — в
`~/.config/systemd/user/fileward.service`, конфигурацию — в
`~/.config/fileward/fileward.conf`. Учитываются `XDG_CONFIG_HOME`, `XDG_STATE_HOME`
и `XDG_RUNTIME_DIR`. JSONL по умолчанию находится в `~/.local/state/fileward/events.jsonl`.
Начальный конфиг только журналирует файлы в отдельном входящем каталоге.

Запускайте установку без `sudo`. Повторный `make install-user` или `make restart-user`
проверяет конфиг, атомарно заменяет бинарь и unit и перезапускает службу.
`make uninstall-user` сохраняет конфигурацию и журналы.

```bash
make health-user
make reload-user
```

Health возвращает код 0 для healthy, 4 для degraded и 3 при недоступности процесса.
Reload возвращает успех после применения нового снимка правил. При отклонении
конфигурации команда завершается кодом 2, а сервис продолжает работать со старой.

Остановить и снова запустить user-service:

```bash
systemctl --user stop fileward.service
systemctl --user start fileward.service
```

У systemd-сервисов нет CLI pidfile: управляйте ими через `systemctl`, а состояние смотрите через `make status-user`.

После изменения правил:

```bash
systemctl --user reload fileward.service
```

Для system-service под конкретным пользователем есть шаблон `systemd/system/fileward@.service`. Перед переходом с user-service остановите его: `systemctl --user disable --now fileward.service`, чтобы один каталог не обрабатывался двумя процессами. Пример установки для текущего пользователя:

```bash
mkdir -p ~/Downloads
meson configure build --prefix=/usr/local --bindir=bin
sudo meson install -C build
sudo install -m 644 systemd/system/fileward@.service /etc/systemd/system/
sudo install -d -m 755 /etc/fileward
sudo install -d -m 700 -o "$USER" "/var/log/fileward/$USER"
if ! sudo test -e "/etc/fileward/$USER.conf"; then
  printf 'watch %s/Downloads\n' "$HOME" | sudo tee "/etc/fileward/$USER.conf" >/dev/null
fi
sudo systemctl daemon-reload
sudo systemctl enable --now "fileward@$USER.service"
```

Системный сервис запускает процесс от имени выбранного пользователя и читает `/etc/fileward/<user>.conf`.

Управление system-service:

```bash
sudo systemctl status "fileward@$USER.service" --no-pager
sudo systemctl reload "fileward@$USER.service"
sudo systemctl restart "fileward@$USER.service"
sudo journalctl -u "fileward@$USER.service" -f
sudo systemctl disable --now "fileward@$USER.service"
```

Для system-service заранее создайте `/var/log/fileward/<user>/` с правами пользователя сервиса. Шаблон ожидает бинарь `/usr/local/bin/fileward`. В отличие от user-service он не задаёт `--state-file`; обычные логи пишет в journal.

## Пример конфигурации

Полный пример правил и действий находится в `example.conf`. Ниже — минимальный фрагмент старого синтаксиса, который также поддерживается.

```text
watch ~/Downloads

when created *.pdf move ~/Documents/PDF
when created *.txt log "text file created"
```

Самостоятельный пример проверки в отдельном временном каталоге:

```bash
demo_dir=$(mktemp -d)
mkdir "$demo_dir/watch"
printf 'watch %s/watch\nwhen created *.txt log "example"\n' "$demo_dir" > "$demo_dir/fileward.conf"
touch "$demo_dir/watch/report.txt"
./build/fileward test --config "$demo_dir/fileward.conf" "$demo_dir/watch/report.txt"
./build/fileward explain --config "$demo_dir/fileward.conf" --event created "$demo_dir/watch/report.txt"
```

Быстрый запуск в фоне:

```bash
mkdir -p ~/Downloads/FilewardLab/{inbox,staging} "$HOME/.local/state/fileward"
./build/fileward start --config example.conf \
  --pidfile "$HOME/.local/state/fileward/fileward.pid" \
  --log-file "$HOME/.local/state/fileward/fileward.log" \
  --state-file "$HOME/.local/state/fileward/fileward.state"
```

Проверка состояния:

```bash
./build/fileward status --pidfile "$HOME/.local/state/fileward/fileward.pid"
```

Перезагрузка правил:

```bash
./build/fileward reload --pidfile "$HOME/.local/state/fileward/fileward.pid"
```

Просмотр логов и журнала действий:

```bash
tail -f "$HOME/.local/state/fileward/fileward.log"
tail -n 20 "$HOME/.local/state/fileward/fileward.state"
```

`Ctrl+C` завершает просмотр `tail -f`. Остановить сам демон:

```bash
./build/fileward stop --pidfile "$HOME/.local/state/fileward/fileward.pid"
```

Во всех командах управления указывайте один и тот же pidfile. По умолчанию используется `/tmp/fileward.pid`; явный путь в пользовательском каталоге позволяет разделять экземпляры. Pidfile остаётся после остановки: блокировка файла показывает, работает ли процесс. Не удаляйте его, пока процесс работает. Повторный `start` с тем же pidfile завершится с ошибкой, пока первый экземпляр активен.

State-file создаётся при первом успешном действии и содержит строки `время<TAB>событие<TAB>watch<TAB>относительный путь<TAB>действие`. `dry-run`, пропуски `conflict=skip`, действия с ошибкой и события без совпавшего правила не добавляют записи. Имена действий в журнале: `log`, `move`, `copy`, `archive`, `exec`. Это журнал, а не очередь для восстановления после перезапуска. Без `--log-file` фоновый процесс отправляет вывод в `/dev/null`.

### Именованные правила в v0.7

Старые строки `when ...` остаются рабочими и включёнными. Для имени и переключателя используйте:

```text
watch ~/Downloads

rule pdfs when created **/*.pdf move ~/Documents/PDF
rule text-log enabled when created *.txt log "text file created"
rule images disabled when created **/*.png move ~/Pictures/Incoming
```

Формат: `rule <name> [options...] when <event> <pattern> <action> [argument]`.
По умолчанию правило включено. Имя уникально, чувствительно к регистру, содержит от 1 до 63 символов: латинские буквы, цифры, `_`, `-`, `.`. Для старых строк `when` автоматически формируется имя `@line-N` по номеру строки; оно может меняться при редактировании конфига. Для постоянных имён используйте `rule`.

Отключённые правила проходят проверку синтаксиса, но не выполняются и не записывают действия в state-file. Включение, отключение, условия, фильтры и режим выполнения применяются через обычный reload. Обычные логи показывают имя и строку сработавшего правила; формат state-file сохранён.

`explain` показывает правила в порядке выполнения, их приоритеты и первую причину пропуска: фильтр пути, остановка цепочки, отключение, другое событие, несовпадение пути/имени/расширения или условие по метаданным. `test` выводит только выполняемые совпадения для `created`. Обе команды и работающий демон используют общий механизм сопоставления.

### Условия правил

Параметры указываются после имени правила, перед `when`, в любом порядке. Все условия одного правила объединяются через И. Повторение параметра и противоречивые границы отклоняются при загрузке конфига.

```text
watch ~/Downloads

rule reports priority=20 type=file name=report-* extension=pdf min-size=1KiB max-size=20MiB min-age=30s max-age=7d when moved_to ** move ~/Documents/Reports
rule recent-text max-age=5m extension=txt when modified ** log "recent text changed"
rule folders type=directory when created ** log "directory created"
```

| Параметр | Значение и поведение |
| --- | --- |
| `name=<glob>` | Шаблон только имени объекта, без каталогов; до 255 байт |
| `extension=<ext>` | Последнее расширение без точки; `pdf` и `.pdf` равнозначны; до 63 байт |
| `type=any\|file\|directory\|symlink` | Тип объекта, по умолчанию `any`; симлинки не разыменовываются |
| `min-size=<N>`, `max-size=<N>` | Включительные границы размера в байтах; суффиксы `B`, `KiB`, `MiB`, `GiB` |
| `min-age=<N>`, `max-age=<N>` | Включительные границы возраста с момента изменения (`mtime`); секунды либо суффиксы `s`, `m`, `h`, `d` |

Числа размера и возраста — неотрицательные целые; после применения единицы максимум равен `INT64_MAX`. Без суффикса используются байты или секунды. Имя и расширение сравниваются с учётом регистра. У `archive.tar.gz` расширение `gz`, у `.env` расширения нет. Для размера обычных файлов рекомендуется `type=file`: размер каталога или симлинка берётся из `lstat` и имеет системный смысл.

Метаданные снимаются один раз на событие до выполнения действий, поэтому последующий `move` не меняет результаты условий для того же события. Если объект недоступен, правило с условиями размера, возраста или типа пропускается с причиной `metadata unavailable`; правила только по имени/пути/расширению могут сработать. Для `deleted` и `moved_from` метаданные всегда считаются недоступными, даже если путь уже занят новым файлом. Будущее `mtime` даёт возраст 0; точность возраста — секунды.

`min-age` — проверка на момент события, а не отложенная задача: демон не ждёт достижения возраста и не запускает правило по таймеру. Для created/modified по умолчанию включено ожидание close_write и стабильности; модификации ожидающего пути объединяются. Подробности и ограничения — в разделе v0.9 ниже. Событие `moved_to` удобно для файлов, подготовленных вне наблюдаемого дерева и затем перенесённых в него.

### Приоритеты и цепочки

```text
watch ~/Downloads
mode all

rule special priority=100 stop name=important-* when created ** log "special file"
rule normal priority=10 when created ** log "normal file"
rule fallback priority=-10 when created ** log "fallback"
```

- `priority=<integer>`: от `-2147483648` до `2147483647`, по умолчанию 0. Большее значение выполняется раньше; при равенстве действует порядок строк в конфиге.
- `mode all` (по умолчанию): выполнить все совпавшие правила.
- `mode first`: выполнить первое совпавшее правило и завершить цепочку.
- `stop`: завершить цепочку после совпадения именно этого правила, в том числе в `mode all`.

Остановка происходит после попытки действия, включая ошибку и `dry-run`. В `mode all` без `stop` ошибка действия не мешает последующим правилам. Метаданные исходного объекта сохраняются для проверок, но действия выполняются последовательно над исходным путём: несколько `move` одного файла могут завершаться ошибкой после первого перемещения. `explain` прогнозирует проверки и порядок, но не успех файловых операций.

### Списки путей

```text
watch ~/Downloads
ignore **/*.part
ignore cache/**
allow **/*.pdf
allow **/*.txt
deny private/**

when created ** log "allowed file"
```

Директивы `ignore`, `allow`, `deny` принимают один glob-шаблон пути относительно `watch`. Можно задать суммарно до 64 фильтров. Сначала проверяется `ignore`, затем `deny`, затем `allow`: совпадение с `ignore` или `deny` исключает событие независимо от разрешений. Если есть хотя бы одна строка `allow`, путь должен совпасть хотя бы с одним разрешением. При отсутствии `allow` разрешены все пути, не исключённые остальными фильтрами.

Фильтры применяются ко всем событиям, в том числе при отсутствии правил. Они не отключают рекурсивное наблюдение за каталогами. Чтобы исключить содержимое каталога, используйте `cache/**`, а не только `cache`. Порядок строк фильтров не меняет их приоритет. `explain` показывает `path ignored`, `path denied` или `path not in allow list`.

`test` требует существующий объект (включая симлинк без доступной цели). `explain` допускает отсутствующий последний компонент, если родительский каталог существует, поэтому можно объяснять `deleted` и `moved_from`. Родительские каталоги разрешаются через `realpath`, а последний компонент сохраняется: симлинк проверяется как запись внутри `watch`; путь через родительский симлинк наружу отклоняется.

### Строгая проверка конфигурации

Во всех режимах, включая reload, ошибками считаются:

- неизвестная директива, событие или действие;
- повторный `watch` или повторяющееся имя правила;
- неверное имя, переключатель, параметр, единица измерения или числовое значение правила;
- повторные параметры, противоречивые границы размера/возраста, повторный или неизвестный `mode`;
- пустой фильтр, лишние аргументы фильтра или больше 64 фильтров;
- недостающий аргумент действия, незакрытая кавычка сообщения/пути/команды;
- неизвестный шаблон назначения/аргумента, неверная политика конфликта или неприменимые к действию опции;
- лишний текст после назначения файлового действия или закрывающей кавычки `log`;
- строка длиннее 1023 байт (без `\n`) или больше 64 правил.

Комментарии поддерживаются отдельными строками, начинающимися с `#`. У `log` без кавычек весь остаток строки — текст сообщения. Проверка конфигурации не проверяет грамматику glob-шаблонов отдельно от сопоставления.

**Изменение относительно v0.6:** неизвестные директивы и повторные `watch` раньше давали предупреждение, теперь конфиг отклоняется. Исправьте такие строки перед обновлением. При неудачном reload продолжают работать предыдущие правила.

В этом этапе конфигурация поддерживает:

- `watch <path>` — каталог для наблюдения
- `when <event> <pattern> move <target>` — перемещение совпадающих файлов
- `when <event> <pattern> log "message"` — логирование события
- glob-паттерны `**/*.txt` для вложенных директорий
- путь внутри watch-дерева, например `docs/**/*.md`

События: `created`, `modified`, `deleted`, `moved_from`, `moved_to`. Шаблон сравнивается с путём относительно `watch`: `*.txt` — файлы в корне, `**/*.txt` — также во вложенных каталогах. Поддерживается один `watch`; правила выполняются по приоритету, а при равенстве — в порядке записи с учётом `mode` и `stop`. Строки, начинающиеся с `#`, считаются комментариями. Пути назначения файловых действий с пробелами заключаются в одинарные или двойные кавычки.

## Действия v0.8

Общий пример всех возможностей — `example.conf` (рабочая локальная копия — `fileward.conf`). Все назначения `move`, `copy`, `archive` задают **каталог**, к которому исполнитель добавляет исходное имя файла; `archive` также добавляет `.gz`. Относительные пути считаются от рабочей папки запуска. `~/` раскрывается в начале каталога назначения.

```text
watch ~/Downloads/FilewardActions/inbox
mode all

rule backup priority=30 type=file conflict=rename when moved_to ** copy "~/Downloads/FilewardActions/backup/{date}/{ext}/{dir}"
rule compress priority=20 type=file extension=txt when moved_to ** archive ~/Downloads/FilewardActions/compressed
rule notify priority=10 timeout=5s when moved_to ** exec /usr/bin/logger --tag fileward -- "{path}"
rule finish stop type=file conflict=rename when moved_to ** move "~/Downloads/FilewardActions/processed/{ext}"
```

### Файловые действия

| Действие | Результат |
| --- | --- |
| `copy <directory>` | Копия обычного файла; исходник остаётся |
| `archive <directory>` | Gzip-копия одного обычного файла `<name>.gz`; исходник остаётся |
| `move <directory>` | Перемещение файла; для обычного файла поддержан переход между файловыми системами |

`archive` — сжатие одного файла через zlib, без внешней команды `gzip`. Это не tar/zip и не упаковка каталогов. `copy`/`archive` не следуют симлинкам и отклоняют каталоги, FIFO и устройства. `move` поддерживает обычные файлы и симлинки в пределах одной файловой системы; межфайловый перенос симлинков и перенос каталогов не поддержаны.

`copy`/`archive` сначала записывают скрытый временный файл в каталоге назначения. После проверки исходника, закрытия и `fsync` результат публикуется переименованием. Частичный файл не становится конечным назначением при ошибке записи; временный файл удаляется при обработанных ошибках. Изменение размера/mtime/ctime исходника во время чтения приводит к ошибке `EAGAIN` и ограниченному повтору. Это проверка стабильности во время копирования, а не ожидание окончания загрузки.

Копируются байты, обычные биты прав доступа и времена atime/mtime; владелец результата — пользователь демона. ACL, xattr, исходный владелец, специальные биты прав, структура hardlink и разрежённость файла не сохраняются. Для gzip времена и права применяются к `.gz`, исходное имя и метаданные отдельно в gzip-заголовке не сохраняются.

При межфайловом `move` исходник удаляется только после публикации копии и повторной проверки его состояния. Если источник изменился или его не удалось удалить после публикации, действие завершается ошибкой, опубликованная копия остаётся, повтор всей операции не производится. Операция между разными файловыми системами не является единым атомарным действием. Параллельную запись/замену источника другими процессами следует исключить в сценариях перемещения.

### Конфликты назначения

Укажите опцию перед `when`: `rule name conflict=rename when ... copy ...`.

| Политика | Поведение |
| --- | --- |
| `conflict=fail` | По умолчанию: ошибка, существующее назначение сохраняется |
| `conflict=skip` | Пропустить действие и сохранить исходник; записи об успехе в state-file нет |
| `conflict=rename` | Подобрать свободное имя `<name>.1`, `<name>.2`, …, до 1000 суффиксов |
| `conflict=overwrite` | Явно разрешить атомарную замену записи назначения |

Для `fail`/`skip`/`rename` используется Linux `renameat2(RENAME_NOREPLACE)`, который исключает перезапись при гонке за имя; файловая система должна поддерживать эту операцию. При `overwrite` конечный симлинк заменяется как запись, его цель не открывается. Источник и назначение, указывающие на один inode, отклоняются. Родительские каталоги назначения считаются доверенной конфигурацией и могут содержать симлинки.

**Изменение относительно v0.7:** `move` теперь по умолчанию не перезаписывает одноимённый файл. Старые конфиги разбираются, но для прежнего поведения требуется явный `conflict=overwrite`. Перенос каталогов больше не поддерживается; используйте условия `type=file` или `type=symlink`.

### Повторы и задержка между попытками

`retries=0..5` — число дополнительных попыток для `move`/`copy`/`archive`, по умолчанию 2. `backoff=1ms..5000ms` — начальная задержка, по умолчанию `100ms`. Задержка удваивается после каждой ошибки, максимум 5000 мс.

Повторы выполняются для `EINTR`, `EAGAIN`, `EBUSY`, `ETXTBSY`, `EMFILE`, `ENFILE`. Конфликты, отсутствие файла, недостаток прав, места и неподдерживаемые операции не повторяются. `EXDEV` у обычного `move` переключает выполнение на копирование с последующим удалением, вместо повторения одного и того же rename. Повторы и ожидания прерываются при остановке демона.

### Команды exec

```text
rule inspect timeout=10s type=file when moved_to ** exec /usr/bin/stat -- "{path}"
```

Первый аргумент — абсолютный путь к исполняемому файлу без шаблонов. Максимум 32 элемента argv, включая программу. Одинарные/двойные кавычки группируют аргументы; обратный слеш экранирует следующий символ вне одинарных кавычек. Пустые аргументы поддерживаются. Командная строка ограничена общим лимитом строки конфига 1023 байта.

Аргументы сначала разбираются, затем в каждом раскрываются шаблоны. Подставленное имя файла остаётся одним аргументом, даже если содержит пробелы, кавычки или символы shell. Неявного shell, подстановки `$HOME`, конвейеров, перенаправлений и раскрытия `*` нет. Для передачи имён файлов утилитам используйте их разделитель `--`, где он поддерживается. Если явно вызвать shell с `-c`, интерпретацию строки берёт на себя этот shell; шаблоны с именами файлов в такие строки передавать не следует.

Команда работает в одном из рабочих потоков от пользователя демона, с его окружением и рабочим каталогом. stdin направлен в `/dev/null`, stdout/stderr наследуют лог/терминал демона, внутренние дескрипторы watcher/pidfile закрываются. Успех — только код завершения 0. Ошибка запуска, сигнал, ненулевой код и таймаут считаются ошибкой действия. Автоматического повтора `exec` нет: команда могла уже произвести побочный эффект.

`timeout=1s..300s` (также `m`, например `5m`), по умолчанию `30s`. По таймауту или остановке демона группе процессов отправляется SIGTERM, через 200 мс — SIGKILL, основной дочерний процесс собирается через waitpid. После обычного завершения также останавливаются оставшиеся процессы этой группы. Это интерфейс для синхронных утилит; процессы, самостоятельно покидающие группу через setsid/setpgid, таким способом не контролируются.

### Шаблоны назначения и аргументов

| Шаблон | Значение |
| --- | --- |
| `{name}` | Имя файла с расширением |
| `{stem}` | Имя без последнего расширения |
| `{ext}` | Последнее расширение без точки; пусто у `.env` и файлов без расширения |
| `{dir}` | Родительский путь относительно watch; пусто для файла в корне |
| `{relative}` | Полный относительный путь |
| `{root}` | Каталог watch |
| `{path}` | `{root}/{relative}` |
| `{event}` | Тип события |
| `{date}` | Текущая дата обработки в UTC, `YYYY-MM-DD` |

Шаблоны действуют в каталоге назначения `move`/`copy`/`archive` и аргументах `exec`. Для буквальных фигурных скобок используйте `{{` и `}}`. Неизвестный шаблон — ошибка конфига; слишком длинный результат — ошибка действия. Подставленные значения повторно как шаблоны не обрабатываются. Сообщения `log` остаются буквальным текстом.

`--dry-run` раскрывает пути и аргументы, но не создаёт каталогов, копий и архивов, не запускает команды и не пишет state-file. Он не гарантирует доступность источника, отсутствие конфликтов или успех последующего реального выполнения. `explain` показывает тип действия, шаблон и раскрытый каталог назначения, конфликт, retries/backoff или команду/timeout, сохраняя общий порядок правил из v0.7.

## Наблюдаемость и исполнение v0.9

```bash
./build/fileward run --config fileward.conf \
  --journal /tmp/fileward/events.jsonl --workers 4 \
  --queue-size 256 --ready-mode close-write --settle-ms 100
./build/fileward history --journal /tmp/fileward/events.jsonl --limit 20
./build/fileward stats --journal /tmp/fileward/events.jsonl
```

JSONL пишется сразу после получения события и при изменении состояния задания: наблюдение → готовность → проверка правила → начало/результат действия. У записи есть уникальный ID; дочерние записи ссылаются на исходное наблюдение. Поля включают хост, версию конфигурации, путь и его исходные байты Base64, метаданные, назначение, тип результата, код ошибки, errno, exit_code/signal и длительность. Текстовый лог остаётся для человека; для SIEM используйте JSONL.

По умолчанию журнал находится в `$XDG_STATE_HOME/fileward/events.jsonl` либо `~/.local/state/fileward/events.jsonl`. Нескольким экземплярам нужны разные журналы. `--journal-max-bytes` задаёт размер сегмента (64 MiB по умолчанию, сохраняются ещё .1/.2/.3). `--journal-sync` добавляет fdatasync на запись. Журнал, лог, state-file и управляющий сокет должны находиться вне watch; нарушение отклоняется при запуске.

`--workers 1..32` (по умолчанию 4) и `--queue-size 1..4096` (256) управляют пулом. Разные пути обрабатываются параллельно; все правила и события одного пути сериализуются. При reload уже принятые задания сохраняют старую версию правил, новые получают следующую. Переполнение очереди не скрывается: записывается `FW_QUEUE_FULL`.

Для обычного файла `created`/`modified` ожидается закрытие дескриптора записи и стабильность размера/mtime/ctime. `moved_to` использует стабильность, поскольку файл мог быть закрыт до переноса. Каталоги, симлинки и удаления не ждут записи. `--ready-mode stable` использует только стабильность, `immediate` возвращает немедленное поведение старых версий. `--settle-ms` — 0..60000, `--ready-timeout-ms` — 100..3600000 (300000 по умолчанию, больше settle-ms). Недоступный/заменённый файл и истечение ожидания дают кодированную отмену вместо действия.

`history` возвращает последние результаты действий в JSONL; `--all` включает всю цепочку, `--event-id` выбирает событие с его дочерними записями. `stats` возвращает JSON-счётчики по сохранённым сегментам, включая прошлые запуски. Это не бессрочные totals и не транзакционный снимок работающего демона.

Подробности: [архитектура](documentation/architecture.md), [журнал и схема](documentation/observability.md), [JSON Schema](documentation/events.schema.json), [коды ошибок](documentation/errors.md), [интеграции](integrations/README.md).

## Текущие ограничения

- Правила одного пути выполняются последовательно; разные пути обрабатываются параллельно. Локальная запись аудита и операции наблюдения всё ещё могут кратковременно задерживать приём событий. Блокирующий системный вызов не гарантирует мгновенную отмену.
- Каталоги результатов и журналы размещайте вне watch либо явно исключайте их фильтрами, чтобы собственные copy/archive/move не запускали цепочки повторно.
- Временные файлы очищаются при обработанных ошибках; после SIGKILL/сбоя питания возможны оставшиеся `.fileward-*`. Гарантии полной транзакционности и восстановления после сбоя пока нет.
- Готовность определяется close_write/стабильностью, а не знанием протокола загрузчика. Несколько писателей или запись после moved_to требуют согласованного протокола публикации; используйте staging → close → rename.
- На старте добавляются watches для существующих каталогов, но правила для уже лежащих файлов не запускаются. Автоматического восстановления пропущенных событий нет.
- Лимит — 512 наблюдаемых каталогов. Переполнение inotify/очереди действий фиксируется явно, но пропущенные события автоматически не восстанавливаются. Перенос каталога требует переподписки с наблюдаемым окном; существующие файлы не переигрываются.

- журнал успешно обработанных действий в state-file;
- очередь событий с обработкой в основном цикле;
- подтверждение успешного старта демона и ожидание остановки в `stop`.

### v0.7 — расширенные правила (готово)

- условия по размеру, возрасту изменения, имени, расширению и типу объекта;
- имена правил, `enabled`/`disabled` и строгая команда `validate`;
- режимы `all`/`first`, остановка цепочки через `stop`;
- приоритеты с сохранением порядка при равенстве;
- списки `ignore`/`allow`/`deny`;
- общий механизм сопоставления для daemon, `test`, `explain`;
- объяснения пропусков, unit-тесты и интеграционные проверки, включая reload и dry-run.

### v0.8 — расширенные действия (готово)

- `copy`, gzip-копии `archive`, синхронный `exec` с таймаутом;
- политики конфликтов `fail`/`skip`/`rename`/`overwrite`;
- публикация копий/архивов через временный файл, межфайловый `move` обычных файлов;
- ограниченные retries/backoff для временных ошибок;
- шаблоны каталогов назначения и аргументов;
- dry-run, explain, state-file, reload и проверки ошибок для новых действий.

### v0.9 — наблюдаемость (готово)

- версионируемый JSONL-журнал, диагностические события, типизированные причины и коды ошибок;
- история действий и метрики через `history`/`stats`;
- ротация, блокировка единственного писателя, остановка при отказе аудита;
- подготовленные шаблоны Wazuh → Shuffle и проверка их формата;
- пул потоков, сериализация цепочек одного пути, неизменяемые версии config при reload;
- ожидание close_write/стабильности, таймаут готовности, объединение модификаций;
- разделение исходников и тестов по модулям.

### v1.0 — движок локальной автоматизации (готово)

- отдельные интерфейсы watcher, планировщика, исполнителя и состояния;
- модульные обработчики действий с единым реестром возможностей;
- живой health в JSON и ограниченный локальный управляющий сокет;
- подтверждаемый reload с сохранением предыдущих правил при ошибке;
- запуск через systemd с readiness, watchdog, ограничением рестартов и завершением дочерних процессов;
- установка/обновление одной командой, сохранение конфига и журналов, русская документация;
- проверки управляющего протокола, установщика и настоящего systemd.

Интерфейсы расширения описаны в [руководстве разработчика](documentation/extensions.md),
эксплуатация — в [руководстве по развёртыванию](documentation/deployment.md).
