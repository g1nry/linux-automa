# Fileward

**Локальная автоматизация файлов для Linux**

Текущая версия — **v1.1.1**, ветка `v1.1.1-wazuh-fixes`.
Исправления интеграции Wazuh и диагностики запуска: [заметки к выпуску](documentation/releases/v1.1.1.md).
[План развития 1.2–1.10 и TUI](documentation/roadmap.md) ведётся отдельно.

Fileward следит за каталогом через `inotify`, проверяет события по правилам и
выполняет действия: записывает сообщения, копирует и перемещает файлы, создаёт
Gzip-копии или запускает команды. События, результаты и причины ошибок сразу
попадают в структурированный JSONL-журнал. В 1.1 сериализация использует ограниченный
буфер без выделения памяти на каждую запись; [методика и результаты замеров](documentation/performance.md).

Проект подходит для сортировки загрузок, обработки входящих файлов, создания
копий и запуска локальных утилит. Для повседневной работы предусмотрены сервис
systemd, перезагрузка правил и проверка состояния работающего процесса.

```text
Событие → ожидание готовности файла → правила → действия → JSONL-журнал
```

## Быстрый запуск

Команды выполняются **из корня клонированного репозитория**. Для Debian/Ubuntu
с работающим пользовательским systemd:

```bash
sudo apt-get install -y build-essential meson ninja-build pkg-config zlib1g-dev python3
make install-user
make health-user
```

Если зависимости уже установлены, достаточно последних двух команд.
`make install-user` собирает оптимизированный бинарь в `build-release/`, устанавливает
его и запускает службу.
Саму установку сервиса выполняйте **без `sudo`**.

При первой установке создаются каталог `~/Downloads/Fileward/inbox` и конфигурация
с одним действием `log`. Добавьте файл и посмотрите результат:

```bash
touch ~/Downloads/Fileward/inbox/hello.txt
make logs-user
```

Начальное правило журналирует появление файла. Чтобы настроить обработку,
отредактируйте `~/.config/fileward/fileward.conf` и выполните `make reload-user`.
Повторная установка сохраняет существующий конфиг.

Нужны Linux, glibc ≥ 2.34, C-компилятор, Meson, Ninja, Make, pkg-config, zlib и
Python 3. Для режима сервиса нужен пользовательский systemd, доступный через
`systemctl --user`. Запуск в терминале описан в [практическом примере](#проверка-на-практике).

## Возможности

| Область | Что поддерживается |
| --- | --- |
| Наблюдение | Рекурсивный `inotify`; создание, изменение, удаление и перенос объектов |
| Правила | Имена, включение и отключение, приоритеты, условия, фильтры путей, цепочки |
| Действия | `log`, `copy`, `move`, `archive`, `exec`; конфликты, повторы, таймауты и шаблоны |
| Исполнение | Ограниченная очередь и пул потоков; последовательная обработка одного пути |
| Готовность файла | Ожидание закрытия записи и стабильности метаданных с таймаутом |
| Диагностика | JSONL, коды причин, ротация, история, статистика и живой `health` |
| Эксплуатация | User/system services, readiness, watchdog, reload с подтверждением |
| Интеграции | JSONL для внешних коллекторов, шаблоны Wazuh и адаптер Shuffle |

## Управление сервисом

| Задача | Команда |
| --- | --- |
| Установить или обновить и запустить | `make install-user` |
| Проверить состояние движка | `make health-user` |
| Посмотреть состояние службы | `make status-user` |
| Смотреть логи | `make logs-user` |
| Применить изменённые правила | `make reload-user` |
| Пересобрать, установить и перезапустить | `make restart-user` |
| Остановить и удалить службу и бинарь | `make uninstall-user` |

Остановить службу без удаления и запустить снова:

```bash
systemctl --user stop fileward
systemctl --user start fileward
```

Reload подтверждает публикацию нового снимка конфигурации. Уже принятые задания
используют прежние правила, следующие события — новые. При ошибке загрузки сервис
продолжает работать с предыдущей конфигурацией. Изменение каталога `watch` требует
рестарта.

Systemd получает уведомление готовности после запуска наблюдателя, потоков,
аудита и управляющего сокета. Watchdog следит за главным циклом; после сбоя или
его зависания systemd перезапускает процесс с ограничением частоты рестартов.

### Файлы установки

| Файл | Путь по умолчанию |
| --- | --- |
| Бинарь | `~/.local/bin/fileward` |
| Конфигурация службы | `~/.config/fileward/fileward.conf` |
| User unit | `~/.config/systemd/user/fileward.service` |
| JSONL-журнал | `~/.local/state/fileward/events.jsonl` |
| Управляющий сокет | `$XDG_RUNTIME_DIR/fileward/control.sock` |

Учитываются `XDG_CONFIG_HOME`, `XDG_STATE_HOME` и `XDG_RUNTIME_DIR`.
Обновление сохраняет конфиг и журналы; удаление службы также оставляет эти данные.
Для первой установки со своим конфигом используйте `make install-user CONFIG=fileward.conf`.
Параметр `CONFIG` применяется только при отсутствии установленной конфигурации.

Системная служба `fileward@<user>`, установка без запуска, fallback-пути сокета,
работа после выхода из сессии и обновление с предыдущих версий описаны в
[руководстве по развёртыванию](documentation/deployment.md).

## Конфигурация

В репозитории один общий пример — [example.conf](example.conf). Файл
`fileward.conf` предназначен для локальных правил и исключён из Git. Конфигурация
установленной службы хранится по пути из таблицы выше; именно её читает сервис.

Пример цепочки: записать событие, сохранить копию, затем распределить оригиналы:

```text
watch ~/Downloads/FilewardLab/inbox
mode all

ignore **/*.part
ignore **/*.tmp

rule incoming priority=100 type=file when moved_to ** log "Входящий файл"
rule backup priority=50 type=file conflict=rename when moved_to ** copy "~/Downloads/FilewardLab/backup/{date}/{dir}"
rule pdf priority=20 stop type=file extension=pdf conflict=rename when moved_to ** move ~/Downloads/FilewardLab/pdf
rule other stop type=file conflict=rename when moved_to ** move "~/Downloads/FilewardLab/other/{ext}"
```

### Как читается правило

```text
rule <имя> [параметры] when <событие> <шаблон пути> <действие> [аргумент]
```

Параметры задаются **перед `when`**. Поддерживаются `enabled`/`disabled`, `priority`,
`stop`, условия `name`, `extension`, `type`, `min-size`/`max-size`, `min-age`/`max-age`.
Все условия одного правила должны совпасть. Возраст проверяется при передаче
готового задания на исполнение; он не задаёт таймер запуска.

Правила выполняются по убыванию приоритета, при равенстве — по порядку строк.
`mode all` выполняет все совпадения, `mode first` — первое. Параметр `stop`
заканчивает цепочку после попытки действия выбранного правила.

| Событие | Значение |
| --- | --- |
| `created` | Объект появился внутри дерева |
| `modified` | Файл изменён |
| `saved` | Закрыт дескриптор файла, открытый на запись |
| `deleted` | Объект удалён |
| `moved_to` | Объект перенесён в наблюдаемый путь |
| `moved_from` | Объект перенесён из наблюдаемого пути |

Шаблоны сравниваются с путём относительно `watch`: `*.txt` — в корне,
`**/*.txt` — включая вложенные каталоги. Фильтры `ignore` и `deny` исключают пути;
при наличии `allow` требуется хотя бы одно разрешающее совпадение.

### Действия

| Действие | Результат |
| --- | --- |
| `log "сообщение"` | Запись буквального сообщения в диагностический лог |
| `copy <каталог>` | Копия обычного файла |
| `move <каталог>` | Переименование через renameat2; без копирования и удаления при EXDEV |
| `archive <каталог>` | Gzip-копия одного обычного файла с суффиксом `.gz` |
| `exec /absolute/program [args...]` | Синхронный запуск команды с таймаутом |

У файловых действий аргумент задаёт каталог: имя результата берётся из имени
источника. По умолчанию конфликт назначения приводит к ошибке. Доступны
`conflict=fail|skip|rename|overwrite`, а также `retries` и `backoff`.
`exec` поддерживает `timeout` и запускается без неявного shell.

Каталоги назначения и аргументы `exec` поддерживают шаблоны, например
`{name}`, `{ext}`, `{dir}`, `{path}` и `{date}`. Сообщения `log` остаются
буквальным текстом. Для реакции на закрытие записи используйте `when saved`; atomic-save через
временный файл наблюдается как `moved_to`. Закрытие не подтверждает fsync.
Полная грамматика, единицы измерения, все шаблоны и поведение
ошибок — в [справочнике конфигурации](documentation/configuration.md).

## Проверка на практике

Пример ниже использует `example.conf` и отдельный каталог `FilewardLab`.
Его правила копируют файлы, сжимают TXT и перемещают оригиналы; действие `exec`
по умолчанию отключено.

Если установленный сервис уже наблюдает это же дерево, сначала остановите его
через `systemctl --user stop fileward.service`. Одновременные экземпляры могут
повторно выполнить действия над одним файлом.

Соберите программу, подготовьте каталоги и проверьте синтаксис и доступность watch:

```bash
make build
mkdir -p ~/Downloads/FilewardLab/{inbox,staging}
./build/fileward validate --config example.conf --check-watch
```

Запустите просмотр предполагаемых действий:

```bash
./build/fileward run --dry-run --config example.conf \
  --journal /tmp/fileward-lab/events.jsonl \
  --control-socket /tmp/fileward-lab/control.sock
```

Во втором терминале подготовьте и опубликуйте файл:

```bash
printf 'Тестовый отчёт\n' > ~/Downloads/FilewardLab/staging/report.txt
mv ~/Downloads/FilewardLab/staging/report.txt ~/Downloads/FilewardLab/inbox/
```

В первом терминале появятся совпавшие правила и предполагаемые действия.
`--dry-run` ведёт аудит, но не изменяет исходные файлы, не создаёт результаты
действий и не запускает команды. Для настоящей обработки остановите процесс
через `Ctrl+C`, повторите запуск без `--dry-run` и опубликуйте новый файл.
Файлы, уже лежащие в `inbox` на старте, автоматически не обрабатываются.

Для редактирования своей копии примера:

```bash
test -e fileward.conf || cp example.conf fileward.conf
```

Затем указывайте `--config fileward.conf`. Ручной запуск завершается по `Ctrl+C`.
Без конфига, например `./build/fileward run ~/Downloads`, программа журналирует
события без выполнения действий.

## Команды CLI

Команды из дерева проекта доступны через `./build/fileward`; установленный
бинарь — через `~/.local/bin/fileward`.

| Команда | Назначение |
| --- | --- |
| `help`, `--help` | Справка по командам и параметрам |
| `--version` | Версия программы |
| `run` | Наблюдение в терминале |
| `start` | Фоновый запуск с подтверждением готовности |
| `stop --pidfile <путь>` | Остановка отдельного фонового процесса |
| `status --pidfile <путь>` | Проверка процесса по pidfile |
| `health [--socket <путь>]` | Состояние работающего движка в JSON |
| `reload [--socket <путь>]` | Перечитывание конфига с подтверждением результата |
| `validate --config <файл> [--check-watch]` | Синтаксис; с флагом — существование и доступность корня watch |
| `test --config <файл> <путь>` | Совпавшие правила для события `created` |
| `explain --config <файл> --event <событие> <путь>` | Порядок проверки и причины пропуска правил |
| `history` | Последние результаты действий из JSONL |
| `stats` | Счётчики по сохранённым сегментам JSONL |
| `actions` | Зарегистрированные обработчики действий |

Например, для существующего файла из практического примера:

```bash
./build/fileward test --config example.conf ~/Downloads/FilewardLab/inbox/report.txt
./build/fileward explain --config example.conf --event moved_to ~/Downloads/FilewardLab/inbox/report.txt
./build/fileward health --socket /tmp/fileward-lab/control.sock
```

`test` и `explain` не выполняют действий. В примере большинство правил привязаны
к `moved_to`, поэтому их покажет `explain` с этим событием.
Команды `stop` и `status` используют pidfile; службой systemd управляйте через
`systemctl` или цели Makefile. Legacy `reload --pidfile` отправляет SIGHUP без
ожидания результата. [Ручной фоновый запуск](documentation/deployment.md#фоновый-запуск-без-systemd).

Коды завершения **CLI**: `0` — успех, `1` — ошибка аргументов или пути,
`2` — ошибка конфигурации, `3` — ошибка исполнения, журнала или соединения,
`4` — `health` обнаружил состояние `degraded`. Обёртки Make/systemctl могут
возвращать собственные коды. `status` возвращает `0` и для остановленного процесса;
проверяйте его текстовый вывод.

## Журналы и диагностика

| Источник | Для чего нужен |
| --- | --- |
| `journalctl` или `--log-file` | Читаемая диагностика; здесь же вывод дочерних команд |
| `events.jsonl` | Структурированные наблюдения, результаты и причины ошибок |
| `health` | Живое состояние текущего процесса, очереди, потоков и подписок |
| `history` и `stats` | Просмотр сохранённого аудита, включая предыдущие запуски |

Для установленной службы:

```bash
~/.local/bin/fileward health
~/.local/bin/fileward history --limit 20
~/.local/bin/fileward stats
journalctl --user -u fileward.service -p err -n 50 --no-pager
```

Ошибки действий, очереди, готовности и запуска видны в journald с кодом, причиной
и контекстом файла/правила. Для exec указаны статус выхода или сигнал. Настоящие
приоритеты err/warning позволяют фильтровать их через `-p`; подробности и формат —
в [руководстве по журналам](documentation/observability.md#ошибки-в-journalctl).

JSONL содержит версию схемы, ID записи и её родителя, время, хост, путь,
поколение конфигурации, правило, действие, результат, код причины и длительность.
Запись создаётся при наблюдении события и последующих переходах обработки.
Стандартная ротация: 64 MiB на сегмент, текущий файл и ещё три сегмента.
`--journal-sync` добавляет `fdatasync` после каждой записи. Отказ аудита
останавливает дальнейшее исполнение.

Health возвращает `healthy` или `degraded`. Потери событий и уменьшение покрытия
наблюдения сохраняют `degraded` до рестарта. Ошибки отдельных действий отражаются
в счётчике и журнале. `stats` охватывает сохранившиеся сегменты, а счётчики `health`
относятся только к текущему процессу.

### Основные параметры исполнения

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `--workers` | `4` | Число рабочих потоков: 1–32 |
| `--queue-size` | `256` | Общий предел ожидающих и активных заданий: 1–4096 |
| `--ready-mode` | `close-write` | Ожидание записи; также доступны `stable` и `immediate` |
| `--settle-ms` | `100` | Окно стабильности размера/mtime/ctime |
| `--ready-timeout-ms` | `300000` | Предельное время ожидания готовности |
| `--journal` | Каталог состояния пользователя | Путь основного JSONL-журнала |
| `--control-socket` | Runtime-каталог пользователя | Путь локального управления |

Для обычных файлов `created`/`modified` ожидаются закрытие записи и стабильность.
Для `moved_to` используется стабильность: файл мог быть закрыт до переноса.
Разные пути обрабатываются параллельно; события и действия одного пути сериализуются.

Журнал, текстовый лог, совместимый `--state-file` и управляющий сокет должны
находиться **вне `watch`**. Нескольким экземплярам нужны отдельные журналы и сокеты.
Если при ручном запуске указан только `--journal /path/events.jsonl`, сокет по
умолчанию будет `/path/events.jsonl.sock`; передайте этот путь в `health --socket`
или задайте `--control-socket` явно.

Подробнее: [журнал и схема событий](documentation/observability.md),
[health и управление](documentation/deployment.md#живой-health-и-протокол-управления),
[каталог кодов](documentation/errors.md).

## Интеграции с SIEM и SOAR

Основной интерфейс передачи событий — версионированный JSONL. В репозитории есть
шаблоны чтения журнала и правил Wazuh, настройки передачи оповещений в Shuffle
и Python-адаптер нормализации входных данных. Для других SIEM журнал можно читать
внешним коллектором с сопоставлением полей.

Fileward передаёт сведения о локальной автоматизации: что произошло, какое
правило сработало, что выполнилось и почему возникла ошибка. Доставку, авторизацию
и обработку на стороне SIEM/SOAR настраивают отдельно. Локальные проверки шаблонов
не подтверждают сквозную доставку на действующем стенде.

Инструкция: [Fileward → SIEM → SOAR](integrations/README.md).

## Разработка и проверки

```bash
make build
make check
```

`make check` запускает модульные и интеграционные проверки правил, действий,
состояния, аудита, параллельности, готовности файлов, управляющего протокола,
установщика и формата интеграционных шаблонов.

При доступном пользовательском systemd:

```bash
make check-systemd
```

Сценарий использует отдельный временный unit: проверяет readiness, reload,
рестарт после SIGKILL, watchdog после зависания и обработку файлов после восстановления.
Обычная служба `fileward.service` не затрагивается.

В CI выполняются основная проверка и ASan/UBSan. Команды для инструментированных
сборок и ThreadSanitizer — в [руководстве по проверкам](documentation/testing.md).
`make release` собирает оптимизированный бинарь для установки; `make build` — отладочный.
`make help` показывает все цели; `make clean` удаляет отладочный каталог сборки.

### Структура проекта

| Каталог | Назначение |
| --- | --- |
| `src/app/` | CLI, жизненный цикл, управление и уведомления systemd |
| `src/core/` | Конфигурация, правила и glob |
| `src/watcher/` | Наблюдатель inotify |
| `src/runtime/` | Очередь, готовность и рабочие потоки |
| `src/actions/` | Реестр обработчиков, действия и шаблоны |
| `src/observability/` | Аудит, диагностика, состояние и запросы |
| `include/fileward/` | Интерфейсы модулей |
| `tests/unit/`, `tests/integration/` | Модульные и интеграционные проверки |
| `scripts/`, `systemd/` | Установщик и шаблоны служб |
| `documentation/`, `integrations/` | Документация и шаблоны интеграций |
| `third_party/jsmn/` | Закреплённый JSON-парсер с лицензией MIT |

## Ограничения

- На старте существующие файлы не обрабатываются. Очередь не сохраняется на диск;
  после аварии незавершённые задания и пропущенные события автоматически не восстанавливаются.
- Поддерживается до 512 наблюдаемых каталогов. Переполнение inotify или очереди
  заданий фиксируется в аудите и health, но не вызывает повторной обработки потерь.
- Готовность файла определяется по закрытию записи и стабильности метаданных.
  При нескольких писателях или записи после переноса нужен согласованный способ
  публикации: подготовить файл вне `watch`, закрыть его, затем перенести внутрь.
- Действия одного пути последовательны. Запись аудита и операции наблюдения
  могут задерживать главный цикл; блокирующий ввод-вывод не всегда быстро отменяется.
- Обработка строго один раз и откат всей цепочки не гарантируются. После SIGKILL
  возможны временные `.fileward-*`. Между файловыми системами `move` отклоняется с `FW_CROSS_DEVICE_MOVE`.
- Результаты действий размещайте вне `watch`, чтобы их создание не запускало
  новые цепочки. `archive` сжимает один файл; перенос каталогов не поддерживается.
