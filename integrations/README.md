# Fileward -> SIEM -> SOAR

These are configuration templates and a pure payload adapter. They do not install agents,
modify an existing Wazuh manager, or create a workflow on a remote Shuffle instance.
Local tests validate XML syntax and payload transformation; live delivery must be checked
on your own versioned stand.

## Wazuh

1. Run Fileward with an absolute `--journal` path outside its watched tree. Only grant the
   Wazuh collector the read/traverse access it needs: the journal defaults to mode 0600.
2. Add `wazuh/agent-localfile.xml` to the endpoint's `ossec.conf`, replacing USER/path.
   Wazuh's JSON decoder handles each line; a separate custom text decoder is unnecessary.
3. Merge `wazuh/local_rules.xml` into manager local rules after checking IDs 100800..100804
   do not collide with your existing rules. Use `wazuh-logtest` with an actual Fileward line.
4. Restart/reload components according to the deployed Wazuh version and check an action
   failure yields rule 100801, and queue loss yields rule 100802. Successful operations are
   base-level events, not alerts. Forwarding to Shuffle sends alerts, not every raw record.
5. Use a collector that follows renamed files correctly. Fileward rotates to .1/.2/.3;
   configure retention/collection rates so unread segments are not removed. Do not also
   ingest those segments with a wildcard unless deliberate duplicate handling is configured.

Official references:
- https://documentation.wazuh.com/current/user-manual/reference/ossec-conf/localfile.html
- https://documentation.wazuh.com/current/user-manual/ruleset/decoders/json-decoder.html
- https://documentation.wazuh.com/current/user-manual/ruleset/ruleset-xml-syntax/rules.html

## Shuffle

1. Create and start a Webhook trigger; use the URL generated by your deployment, rather
   than guessing a cloud/on-prem endpoint. Configure its authentication as appropriate.
2. Add `wazuh/shuffle-integration.xml` to the manager configuration with that URL. It filters
   by the fileward group and level >= 3. A Fileward audit record is under the alert's `data`.
3. Use the logic in `shuffle/normalize.py` as the first validation/transformation step.
   It accepts direct records or Wazuh envelopes. For a local test:
   `python3 integrations/shuffle/normalize.py < saved-wazuh-alert.json`.
4. Use its dedup_key in a persistent datastore/idempotent destination. Re-delivery of the
   same alert must not create duplicate tickets. Parallel check-then-insert operations
   alone do not provide exactly-once delivery; use the datastore's atomic operation or
   destination idempotency where available.
5. Route failures by code (timeout, permission, conflict, observation loss); enrich metadata
   and create an educational notification/ticket. Never treat path/message values as shell
   commands. The adapter does not upload file contents or execute endpoint actions.

Verify schema rejection, replaying the same alert twice, missing required fields, and an
actual end-to-end alert before claiming stand integration is complete.

Official reference:
https://documentation.wazuh.com/current/user-manual/manager/integration-with-external-apis.html

## Other SIEMs

The versioned JSONL file is independent of Wazuh. Read it with a collector and map
provider -> event.provider, timestamp -> @timestamp, kind -> event.action, outcome -> an
appropriate platform field, and watch_root/relative_path -> file.path. Fileward's outcome
values are not all ECS outcomes: map success/failure directly and classify skipped/ready/
matched separately. Use event_id for delivery deduplication; parent_id correlates rule chains.
