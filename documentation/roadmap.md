# План развития Fileward

Стабильная база — v1.0.0. Рабочая ветка — `v1.1-runtime` (`1.1.0-dev`).
Этапы ниже задают порядок работы и критерии приёмки, а не календарные обещания.
Возможности будущих версий не считаются реализованными, пока не пройдены проверки.
Версии 1.1–1.10 продолжают существующий движок без искусственного перехода на 2.0.

## Приоритеты

1. Измерять задержки, потери, системные вызовы и удержание блокировок на воспроизводимой нагрузке.
2. Сохранять последовательность действий одного пути, ограничение памяти и честный аудит.
3. Отделять долгие команды и файловые операции от приёма событий и управления.
4. Различать изменение, закрытие записи, публикацию через rename и подтверждение сохранности.
5. Не ослаблять проверки файла ради скорости и не скрывать потерю событий.

### v1.1 — убрать лишнюю работу из текущего движка

- Вычислять порядок правил при загрузке снимка, а не для каждого задания.
- Проверять фильтры один раз; разбирать имя и расширение один раз на снимок входных данных.
- Сохранять порядок одного пути между поколениями конфигурации без добавления непроверенного индекса в горячий путь.
- Убрать файловые запросы и аудит ожидания готовности из-под мьютекса очереди.
- Ограничивать частоту readiness-опроса с инвалидацией при закрытии и новых модификациях.
- Добавить `saved` для закрытия writable-дескриптора и атрибуты в `file_closed`.
- Выполнять `move` только через rename; при EXDEV сохранять исходник и возвращать отдельный код причины.
- Устанавливать сервис из оптимизированной сборки отдельно от отладочной.
- Добавить SECURITY.md, тест медленных метаданных и воспроизводимый benchmark без обещания фиксированного ускорения.

**Приёмка:** проверки порядка одного пути, reload, замены inode, таймаутов,
отмены и сохранения; реальные разные файловые системы; ASan/UBSan и TSan;
сравнение с v1.0 с одинаковыми параметрами сборки и аудита. Результат измерений
должен быть опубликован, даже если сценарий не ускорился.

### v1.2 — разделить исполнителей и снять взаимное вытеснение

- Выделить лимиты для `exec`, файловых операций и задач метаданных.
- Ввести индекс путей только после профилирования: эксперимент 1.1 не подтвердил выигрыш на простом потоке и не включён в реализацию.
- Представлять цепочку как состояние: ожидание отдельного исполнителя не должно занимать чужой поток.
- Сохранить единый порядок одного пути, `mode first`, `stop` и поколения правил при переходах между пулами.
- Добавить справедливое обслуживание независимых путей, чтобы один поток событий не занимал всю очередь.
- Перенести readiness-метаданные с главного цикла; результаты возвращать с проверкой поколения и идентичности объекта.
- Перевести retries/backoff в планировщик с дедлайнами вместо сна занятого исполнителя.
- Показывать загрузку каждого класса, длительность ожидания и причины отказа при переполнении.

**Приёмка:** все exec-слоты заняты долгими командами, при этом файл другого пути
обрабатывается и health/reload отвечают. Медленная файловая система не должна
удерживать главный цикл; остановка и reload проверяются во всех состояниях цепочки.

### v1.3 — описывать сохранение как последовательность событий

- Разделить сигналы «изменялся», «закрыт на запись», «опубликован через rename» и «готов к обработке».
- Коррелировать IN_MOVED_FROM/IN_MOVED_TO по cookie с ограниченным временем хранения.
- Обрабатывать сценарий редактора: временный файл → запись → закрытие → замена исходного имени.
- Связывать наблюдения в одну логическую операцию сохранения без удаления исходных audit-записей.
- Добавить политику объединения повторных сохранений и явно определить границы её применимости.
- Проверить несколько писателей, прерванную запись, замену inode, исчезновение временного файла и потерю событий.

**Приёмка:** тесты обычного сохранения и atomic-save дают объяснимые связи,
а закрытие без записи не называется доказанным изменением содержимого.
Гарантии fsync и работы редактора не выводятся только из inotify.

### v1.4 — управляемые снимки атрибутов

- Ввести общую модель device/inode, размера, mode, uid/gid, nlink и времён с наносекундами.
- Проверить применение statx/fstatat с переносимым fallback в рамках поддерживаемого Linux.
- Индексировать известное состояние по пути и идентичности объекта с ограничением памяти.
- Инвалидировать кэш при записи, rename, удалении, потере watch, переполнении и reload.
- Отдавать правилам, аудиту и executor согласованные снимки, сохраняя проверку объекта перед действием.
- Предусмотреть необязательное вычисление хеша отдельным исполнителем с лимитом размера и времени.
- Версионировать расширение схемы и преобразование старых записей, если меняется контракт.

**Приёмка:** меньше системных вызовов на контролируемой нагрузке без пропуска
замены файла, обхода фильтров и использования устаревших атрибутов для разрушительного действия.

### v1.5 — файловый ввод-вывод и большие файлы

- Сравнить буферизованную копию, copy_file_range и доступные средства reflink; выбирать по возможностям файловой системы.
- Сохранить корректный fallback, обработку частичных операций, EINTR, ENOSPC и отмену.
- Определить сохранение sparse-файлов и метаданных как отдельные явные режимы.
- Ввести бюджеты параллельного чтения/записи и измерять влияние на отзывчивость системы.
- Сделать параметры сжатия явными и оценить цену CPU относительно диска.
- Описать durability публикации, включая каталоги, а не только fsync временного файла.
- Сохранить rename-only семантику move; ускорение copy не возвращает скрытый cross-device fallback.

**Приёмка:** большие, sparse и изменяемые источники, заполнение диска и отмена
проверены на нескольких файловых системах; измерены байты, время и потребление памяти.

### v1.6 — конвейер аудита без скрытой потери

- Выделить ограниченную очередь сериализации и записи с понятным backpressure.
- Сохранить условие: действие не начинается без подтверждения требуемой записи аудита.
- Определить порядок записей, flush, shutdown, ротацию и режим подтверждённой синхронизации.
- Показывать очередь аудита, отставание, ошибки и длительность записи.
- Предусмотреть структурированный stdout и внешний коллектор как явно выбираемые режимы.
- Не вводить неблокирующий drop аудита под названием оптимизации.

**Приёмка:** медленный диск и отказ writer не превращаются в неаудируемые действия;
нет взаимной блокировки потоков, потери записей при штатной остановке и нарушения связей ID.

### v1.7 — восстановление и сверка

- Разделить журнал фактов, состояние задания и план повторного выполнения.
- Добавить checkpoint и контролируемую сверку дерева после потери наблюдения или перезапуска.
- Распознавать незавершённые публикации и временные файлы без автоматического удаления неизвестных данных.
- Ввести предварительный просмотр восстановления и явную политику для каждого типа действия.
- Для exec требовать определённой пользователем идемпотентности; не обещать exactly-once внешней команды.
- Проверять сбой до/после публикации и до/после записи результата.

**Приёмка:** fault-injection в точках сбоя; восстановление не удаляет заменённый
источник, не повторяет опасное действие молча и сохраняет след принятого решения.

### v1.8 — интеграции и внешние контракты

- Формализовать отображение событий в выбранные схемы SIEM и сохранить исходный Fileward-контекст.
- Отделить адаптеры доставки от ядра наблюдения и действий.
- Определить ключи дедупликации, подтверждение, повторную доставку и обработку ротации коллекторами.
- Развить примеры Wazuh/Shuffle, добавить стендовые сценарии и проверку неподдерживаемых схем.
- Настраивать секреты и права чтения отдельно от правил работы с файлами.
- Документировать, какие события являются наблюдениями, ошибками автоматизации и оповещениями безопасности.

**Приёмка:** реальный стенд подтверждает доставку, повтор, переподключение и отказ
авторизации; проверка XML/JSON сама по себе не объявляется сквозной интеграцией.

### v1.9 — укрепление границ безопасности

- Перейти к операциям относительно закреплённых дескрипторов каталогов там, где это устраняет гонки пути.
- Оценить openat2/RESOLVE_* и явные политики симлинков для источников и назначений.
- Разделить доверенные корни назначения и права доступа программ exec.
- Добавить необязательные профили systemd и ограничения ресурсов с проверенной совместимостью.
- Проверить конфигурацию, JSON, glob и управляющий протокол fuzz-тестированием.
- Выполнить отдельный обзор модели угроз и подтвердить исправления найденных проблем.
- Уточнить приватный канал сообщений и правила поддержки SECURITY.md с владельцем.

**Приёмка:** воспроизводимые проверки подмены родительских каталогов, гонок inode,
инъекций аргументов и разграничения UID; профили не выдаются за полную песочницу.

### v1.10 — стабилизация и совместимость

- Провести длительные прогоны с высокой частотой событий, утечками ресурсов и отказами диска.
- Утвердить бюджеты p50/p95/p99 задержки, CPU и памяти для описанных профилей нагрузки.
- Зафиксировать поддержку платформ, схем, CLI и пути миграции конфигураций.
- Проверить обновление/откат units и бинаря с сохранением пользовательских данных.
- Завершить эксплуатационные инструкции, диагностику и правила обратного переноса исправлений.
- Отделить экспериментальные возможности от поддерживаемых.

**Приёмка:** воспроизводимый набор совместимости и отказов, опубликованные
ограничения и решение владельца о поддерживаемой ветке. Номер 1.10 не означает
автоматического обещания LTS без такого решения.

## v2.0 — кандидат: интерактивный терминальный интерфейс

Возможный крупный этап — полноэкранный TUI поверх существующего движка:

- состояние службы, очередей и исполнителей в реальном времени;
- просмотр файловых событий и связанных действий;
- фильтрация истории и раскрытие причин ошибки;
- проверка и объяснение правила перед применением;
- редактирование и reload с подтверждением результата;
- клавиатурная навигация, работа без мыши и доступный обычный CLI.

TUI должен обращаться через версионированный локальный API, а не дублировать
планировщик или выполнять произвольные команды через управляющий сокет.
Выбор библиотеки и права на операции управления требуют отдельного проекта.
Новый интерфейс может обосновать 2.0 как изменение способа работы с продуктом;
переписывание ядра и переход на другой язык ради номера не требуются.

## Завершённые этапы

## v0.6 — ядро демона (готово)

- foreground/background режимы запуска;
- pidfile с блокировкой для единственного экземпляра;
- команды `start`, `stop`, `status`, `reload`;
- журнал успешно обработанных действий в state-file;
- очередь событий с обработкой в основном цикле;
- подтверждение успешного старта демона и ожидание остановки в `stop`.

## v0.7 — расширенные правила (готово)

- условия по размеру, возрасту изменения, имени, расширению и типу объекта;
- имена правил, `enabled`/`disabled` и строгая команда `validate`;
- режимы `all`/`first`, остановка цепочки через `stop`;
- приоритеты с сохранением порядка при равенстве;
- списки `ignore`/`allow`/`deny`;
- общий механизм сопоставления для daemon, `test`, `explain`;
- объяснения пропусков, unit-тесты и интеграционные проверки, включая reload и dry-run.

## v0.8 — расширенные действия (готово)

- `copy`, gzip-копии `archive`, синхронный `exec` с таймаутом;
- политики конфликтов `fail`/`skip`/`rename`/`overwrite`;
- публикация копий/архивов через временный файл, межфайловый `move` обычных файлов;
- ограниченные retries/backoff для временных ошибок;
- шаблоны каталогов назначения и аргументов;
- dry-run, explain, state-file, reload и проверки ошибок для новых действий.

## v0.9 — наблюдаемость (готово)

- версионируемый JSONL-журнал, диагностические события, типизированные причины и коды ошибок;
- история действий и метрики через `history`/`stats`;
- ротация, блокировка единственного писателя, остановка при отказе аудита;
- подготовленные шаблоны Wazuh → Shuffle и проверка их формата;
- пул потоков, сериализация цепочек одного пути, неизменяемые версии config при reload;
- ожидание close_write/стабильности, таймаут готовности, объединение модификаций;
- разделение исходников и тестов по модулям.

## v1.0 — движок локальной автоматизации (готово)

- модульные обработчики действий с единым реестром возможностей;
- живой health в JSON и ограниченный локальный управляющий сокет;
- подтверждаемый reload с сохранением предыдущих правил при ошибке;
- запуск через systemd с readiness, watchdog, ограничением рестартов и завершением дочерних процессов;
- установка/обновление одной командой, сохранение конфига и журналов, русская документация;
- проверки управляющего протокола, установщика и настоящего systemd.
