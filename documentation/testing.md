# Проверка реализации

Запустите `make check` из корня репозитория. Команда собирает программу,
выполняет шесть наборов модульных проверок на C: glob, парсер и правила,
исполнитель действий и реестр обработчиков, обработка отказов аудита, параллельная запись состояния. Затем запускаются сценарии исполнения, управления
и установки, а также локальные
проверки XML и адаптера Shuffle.
Проверки используют отдельные временные журналы, не записывают данные в журнал
пользователя по умолчанию, не запускают сервисы и не обращаются к SIEM.

Сценарий v0.9 проверяет:

- удержание писателя открытым дольше интервала стабильности и копирование полного
  содержимого после закрытия;
- появление JSON-записи наблюдения до действий, типы полей схемы, Unicode,
  управляющие символы и некорректные байты в именах;
- ID событий, связи с родителем, назначения, сведения о завершении команд,
  историю и счётчики сохранённых записей;
- длительный `exec` одновременно с обработкой другого пути, reload во время
  исполнения и неизменяемые номера версий конфигурации;
- последовательность цепочек одного пути и одновременную публикацию 60 файлов
  с одинаковыми именами восемью рабочими потоками;
- смену цели симлинка корня, потерю корневого наблюдения и освобождение
  дескрипторов после удаления 280 каталогов;
- заполнение очереди, таймауты готовности, отмену и перезапуск;
- ротацию, некорректные данные запросов, отказ запуска с незавершённым хвостом
  и блокировку единственного писателя;
- реальный отказ записи при `RLIMIT_FSIZE` с последующим завершением процесса кодом 3;
- отклонение журнала внутри наблюдаемого дерева, которое создало бы обратную связь
  из собственных событий программы.

Проверка с ASan/UBSan и трактовкой предупреждений компилятора как ошибок
также настроена в CI:

```sh
meson setup build-asan -Db_sanitize=address,undefined -Dwerror=true
meson compile -C build-asan
meson test -C build-asan --print-errorlogs
python3 tests/integration/observability-smoke.py ./build-asan/fileward
python3 tests/integration/actions-smoke.py ./build-asan/fileward
```

Для ThreadSanitizer нужна совместимая комбинация хоста, ядра и размещения памяти
среды исполнения:

```sh
meson setup build-tsan -Db_sanitize=thread -Dwerror=true
meson compile -C build-tsan
python3 tests/integration/observability-smoke.py ./build-tsan/fileward
```

Нагрузочные проверки с инструментированием могут выявлять гонки на выполненных
путях, но не доказывают отсутствие всех возможных гонок. Выполнение декодеров
и правил Wazuh, обработка ротации и переподключений реальным коллектором,
исполнение и аутентификация сценария Shuffle, устранение повторов доставки
требуют действующего стенда. Локальные проверки шаблонов не подтверждают
сквозную доставку. Подробности — в [руководстве по интеграциям](../integrations/README.md).

## Проверки v1.0

`make check` дополнительно проверяет health живого процесса, права сокета,
ограничение idle-клиентов, успешный reload и отказ с сохранением поколения,
статус degraded при заполнении очереди и недоступность после остановки.
Установщик проверяется с отдельными HOME/XDG и `--no-start`: первая установка,
обновление с сохранением конфига, отказ при ошибочном конфиге, удаление с сохранением
данных, пути с пробелами, `$` и `%`. Сгенерированный unit проверяет systemd-analyze.

При доступном пользовательском systemd выполните:

```sh
make check-systemd
```

Сценарий создаёт unit `fileward-smoke-<pid>.service` во временном каталоге,
проверяет readiness и несколько интервалов heartbeat без ложного рестарта,
reload с подтверждением, отказ ошибочной конфигурации без остановки службы,
автоматический рестарт после SIGKILL и watchdog после SIGSTOP главного процесса,
а затем обработку нового файла и штатную остановку. После проверки unit удаляется.
Обычный `fileward.service` не затрагивается. В CI эта проверка отдельно не запускается:
на runner может отсутствовать пользовательский manager; модуль уведомлений проверяется
на реальном локальном systemd командой выше.

Для инструментированных сборок дополнительно запускайте:

```sh
python3 tests/integration/control-smoke.py ./build-asan/fileward
meson test -C build-tsan --print-errorlogs
python3 tests/integration/control-smoke.py ./build-tsan/fileward
```

## Проверки ветки 1.1

`runtime-test` задерживает настоящий вызов получения метаданных через link-wrapper
lstat/lstat64 и проверяет, что другой поток может получить runtime_status,
а уже запущенное действие — завершиться. Это проверка освобождения мьютекса очереди,
а не обещание, что управляющий сокет главного цикла отвечает при любом зависшем I/O.

`saved-smoke.py` проверяет открытого писателя, полный размер в file_closed,
правило saved после закрытия, закрытие без записи, atomic replacement через moved_to
и поколение конфигурации после reload. Тест действий сохраняет inode при rename,
проверяет отсутствие чтения для копирования и отказ EXDEV на настоящем втором mount,
если он доступен. Обе модели сохранения описаны в [конфигурации](configuration.md).

Методика и команда benchmark: [производительность](performance.md).

Оптимизированная сборка проверяется отдельно: `make release`, затем
`meson test -C build-release --print-errorlogs` и сценарии saved/observability
с `./build-release/fileward`. Assert в этом профиле не отключён, поэтому
проверки с побочными эффектами внутри assert продолжают выполняться.
