# Производительность и планировщик

Изменения относятся к рабочей ветке `v1.1-runtime` (`1.1.0-dev`).
Цель — убрать повторные вычисления и удержание общей блокировки при вводе-выводе.
Это не обещание одинакового ускорения для любой нагрузки.

## Что изменено

| Участок | v1.0 | Рабочая ветка 1.1 |
| --- | --- | --- |
| Порядок правил | Сортировка для каждого задания | Готовый порядок в снимке конфигурации |
| Фильтры пути | Повторная проверка одного события | Один результат проверки |
| Имя и расширение | Повторный разбор при оценке правил | Разбор один раз в rule_input |
| Зависимость одного пути | Проверка предшествующих и активных заданий | Та же проверка с ранним выходом; индекс пока отложен |
| Readiness I/O и аудит | Под общим мьютексом очереди | Вне мьютекса; связи списка читаются заново после возврата |
| Проверка readiness | Каждый проход для каждого задания | Интервал 50–250 мс с инвалидацией по событиям |
| Пробуждение потоков | В том числе на пустом tick | При готовой работе и непустой очереди, без пустого tick |
| Установка сервиса | Обычная отладочная сборка | Отдельный оптимизированный build-release |

Проверка inode перед действием и проверка источника во время копирования
сохраняются. Эксперимент с индексом путей не подтвердил выигрыш в сценарии
независимых файлов и не включён в текущую реализацию. Повторная оценка индекса
запланирована вместе с разделением исполнителей.

## Сборка для установки

```sh
make release
./build-release/fileward --version
```

`make release` создаёт отдельную сборку Meson `--buildtype=release` с оптимизацией
компилятора. `make install-user` и `make restart-user` используют её бинарь.
Отладочная сборка `make build` остаётся в `build/`. Это разные профили компиляции,
а не разные продуктовые версии; суффикс `-dev` сохраняется у рабочей ветки.
Проверки assert оставлены включёнными через `-Db_ndebug=false`.

Не сравнивайте изменение алгоритма по одному отладочному и одному оптимизированному
бинарю. Для оценки кода нужны одинаковые compiler/buildtype/sanitize/настройки
журнала. Для оценки установки полезно отдельно сравнить фактически используемые профили.

## Воспроизводимый сценарий

```sh
python3 tests/bench/runtime.py ./build-release/fileward --files 600 --runs 5
python3 tests/bench/runtime.py /path/to/baseline/fileward ./build-release/fileward --files 600 --runs 5
```

Сценарий создаёт изолированные каталоги и дважды не использует одни и те же
данные. Готовые маленькие файлы публикуются rename из staging в inbox. Работают
64 правила, четыре потока, immediate readiness и очередь 4096. Для каждого файла
проверяются правила, одно действие log выполняется, результаты пишутся в JSONL.
Очерёдность бинарей меняется между прогонами.

Проверяются завершение всех цепочек, отсутствие потерь и ошибок действий.
Вывод содержит отдельные времена, медиану и число файлов в секунду. Подготовка
файлов, запуск и штатный fsync при остановке не входят в интервал. Ожидание health
и его запуск как CLI входят в измерение; точность ограничена в том числе опросом.
`--journal-sync` выключен: это не тест долговечности каждой записи после сбоя питания.

Это сценарий независимых путей и большого количества записей аудита. Он не
заменяет измерения больших файлов, длительного exec, повторных сохранений,
сетевой файловой системы и p95/p99 времени ответа управления. Счётчики ядра
inotify не позволяют считать произвольный поток повторных публикаций одного имени
по числу исходных операций: одинаковые события могут объединяться.

## Локальные измерения

Результаты приведены ниже для одинаковой нагрузки и этого хоста. Они не являются
порогами CI. Сравнение профилей не выдаётся за выигрыш одного алгоритма.

600 файлов, 64 правила, 4 потока, 5 чередующихся прогонов; Linux, GCC 14.2,
Meson release, обычный локальный JSONL без journal-sync. Базовый исходник —
`2ed0f39` (v1.0), сравниваемый — рабочая ветка 1.1.

| Бинарь | Медиана, с | Файлов/с | Отдельные времена, с |
| --- | ---: | ---: | --- |
| v1.0 release | 0.5778 | 1038.43 | 0.5778, 0.6030, 0.5720, 0.5767, 0.6256 |
| 1.1-dev release | 0.6442 | 931.41 | 0.6389, 0.6452, 0.6442, 0.6571, 0.6368 |

В этом сценарии медиана времени рабочей ветки отличается на +11.5% от базы.
Прирост общей пропускной способности не подтверждён; этот результат требует
дальнейшего профилирования до объявления релиза 1.1. Количество файлов и правила
одинаковы; сокращение аудита не использовалось как способ улучшить цифры.

Отладочные прогоны не подтвердили универсального ускорения. Поэтому ветка
остаётся `1.1.0-dev`, а скорость рассматривается по профилям нагрузки.
Упрощённые проверки зависимостей и отсутствие I/O под мьютексом проверяются
отдельно от общего количества файлов в секунду.

## Проверка блокировок

`tests/unit/runtime-test.c` задерживает lstat/lstat64 при ожидании одного файла.
Во время задержки другая нить получает runtime_status, а активное действие
завершается. Второй сценарий проверяет, что отмена неготовой головы пути
освобождает готовое следующее задание и будит исполнителя.

Это проверка мьютекса очереди. Синхронный lstat всё ещё выполняется главным
циклом, а запись аудита остаётся синхронной; медленная файловая система может
задерживать обработку управляющего сокета и reload. Все exec и файловые действия
пока используют общий пул. Перенос метаданных из главного цикла, отдельные классы
исполнителей и backpressure запланированы в [roadmap](roadmap.md).

Для вывода о следующей оптимизации нужны измерения CPU, системных вызовов,
памяти, задержек очереди и управления, а также отдельная нагрузка с долгими командами.
Одно удачное время benchmark не отменяет эти ограничения.
