# Производительность Fileward 1.1

В 1.1 сокращены затраты сериализации JSONL и повторные вычисления при обработке
событий. Полнота аудита, порядок записей, ротация и journal-sync сохраняются.
Приведённые результаты относятся к описанным нагрузкам и этому хосту.

## Что изменено

| Участок | v1.0 | v1.1 |
| --- | --- | --- |
| Сериализация JSON | open_memstream, выделение памяти и множество вызовов stdio на запись | Один ограниченный буфер, копирование печатаемого ASCII блоками |
| Порядок правил | Сортировка для каждого задания | Готовый порядок в снимке конфигурации |
| Фильтры пути | Повторная проверка одного события | Один результат проверки |
| Имя и расширение | Повторный разбор при оценке правил | Разбор один раз в rule_input |
| Зависимость одного пути | Проверка предшествующих и активных заданий | Та же проверка с ранним выходом; индекс пока отложен |
| Readiness I/O и аудит | Под общим мьютексом очереди | Вне мьютекса; связи списка читаются заново после возврата |
| Проверка readiness | Каждый проход для каждого задания | Интервал 50–250 мс с инвалидацией по событиям |
| Пробуждение потоков | В том числе на пустом tick | При готовой работе и непустой очереди, без пустого tick |
| Запрос stats | Накопление истории последних строк | Только счётчики, без массива истории и strdup записей |
| Установка сервиса | Обычная отладочная сборка | Отдельный оптимизированный build-release |

На 600 файлов и 64 правила создаётся 42003 записи. Удаление динамического FILE,
выделения памяти и посимвольного stdio на каждой из них уменьшает работу,
выполняемую под мьютексом аудита. Количество записей не сокращается.
Это оптимизация формирования одной строки; очередь отложенной записи не вводится.
Проверка inode перед действием и проверка источника во время копирования сохранены.

## Сборка и воспроизведение

```sh
make release
./build-release/fileward --version
python3 tests/bench/runtime.py ./build-release/fileward --files 600 --rules 64 --workers 4 --runs 7
python3 tests/bench/runtime.py /path/to/v1.0/fileward ./build-release/fileward --files 600 --rules 64 --workers 4 --runs 7
```

Базовый бинарь собран из `2ed0f39`, прежний снимок 1.1 — из `7ed3a2a`.
Исходники измеренной 1.1.0 — `a9fa20d`; последующие изменения документации
не меняют исполняемый код. Все сравниваемые бинарные файлы используют GCC 14.2.0, Meson release и
`-Db_ndebug=false`, без санитайзеров. `make install-user` и `make restart-user`
используют release-бинарь; отладочный `make build` остаётся в `build/`.

Дополнительные профили:

```sh
python3 tests/bench/runtime.py /path/to/v1.0/fileward ./build-release/fileward --files 2000 --rules 1 --workers 4 --runs 5
python3 tests/bench/runtime.py /path/to/v1.0/fileward ./build-release/fileward --files 600 --rules 64 --workers 1 --runs 5
python3 tests/bench/runtime.py /path/to/v1.0/fileward ./build-release/fileward --files 50 --rules 4 --workers 4 --runs 3 --journal-sync
```

Сценарий создаёт отдельные временные каталоги. Готовые маленькие файлы публикуются
rename из staging в inbox; используется immediate readiness и очередь 4096.
Правила проверяются для каждого файла, одно действие log совпадает. Очерёдность
бинарей меняется между прогонами.

Таймер включает публикацию файлов, исполнение, аудит и ожидание health.
Подготовка, запуск процесса, проверка stats и штатный fsync при остановке не входят
в интервал. После измерения проверяются число наблюдений и завершений, полное
число проверенных правил, успех всех действий, отсутствие потерь и повреждённых
записей. JSON-вывод содержит времена, медиану, счётчики аудита, CPU и peak RSS.
CPU считывается из /proc после измерения и включает время процесса с момента
старта; внешняя команда stats в него не входит. Метрики /proc необязательны.

## Локальные результаты

Все значения ниже — медианы; числа не задают порог CI. При journal-sync=false
сценарий не измеряет сохранность каждой записи после отключения питания.

| Профиль | Файлы / правила / потоки | Прогоны | v1.0, с | v1.1, с | Ускорение | Записей аудита у каждой версии |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| Много правил | 600 / 64 / 4 | 7 | 0.6004 | 0.3033 | 1.98× | 42003 |
| Одно правило | 2000 / 1 / 4 | 5 | 0.2720 | 0.1636 | 1.66× | 14003 |
| Один поток | 600 / 64 / 1 | 5 | 0.5209 | 0.2316 | 2.25× | 42003 |
| journal-sync | 50 / 4 / 4 | 3 | 0.0653 | 0.0585 | 1.12× | 503 |

В основном профиле обе версии проверили 38400 правил и успешно выполнили
600 действий. Все 42003 записи аудита сохранены у каждого бинаря в каждом прогоне.
Чистый log-набор с одним потоком здесь быстрее четырёх: больше потоков не означает
линейного ускорения, когда запись журнала остаётся общей.

### Снятие регрессии первоначальной 1.1

В предыдущем измерении рабочей ветки была обнаружена регрессия около 11,5%.
В свежем общем прогоне получены следующие медианы:

| Снимок | Медиана, с | Файлов/с |
| --- | ---: | ---: |
| v1.0 | 0.6004 | 999.37 |
| 1.1 до оптимизации (7ed3a2a) | 0.6237 | 962.04 |
| v1.1.0 | 0.3033 | 1978.01 |

Финальная оптимизация устраняет регрессию в этом сценарии. Отдельные прогоны,
CPU, RSS и счётчики сохранены в [данных измерений](benchmarks/v1.1.json).
Короткий sync-тест особенно чувствителен к опросу health и задержкам диска;
его относительное отличие не следует переносить на другие файловые системы.

## Проверки и оставшиеся границы

`tests/unit/runtime-test.c` задерживает lstat/lstat64: другая нить получает
runtime_status и завершает действие без ожидания мьютекса очереди. Есть проверки
освобождения готового следующего задания после отмены головы, объединения
модификаций симлинка и снижения числа readiness-проб на частых idle-tick.

`audit-test` проверяет EINTR, короткие записи, сохранение errno, строку размером
131072 байта и отказ большей строки без усечённого JSON. `journal-boundary.py`
проверяет согласованность предела writer/history/stats. Сценарии saved,
observability и действий проходят в обычной, release и инструментированных сборках.

Синхронный lstat остаётся в главном цикле, аудит — синхронным, а действия используют
общий пул. Медленный диск всё ещё может задержать управляющий сокет и reload.
Раздельные исполнители, перенос метаданных из главного цикла и управляемый
backpressure остаются задачами [следующих версий](roadmap.md).

Эти нагрузки не заменяют измерения больших файлов, длительного exec, сетевого
хранилища и p95/p99 ответа управления. Имена с повторными публикациями требуют
отдельного сценария: inotify может объединять одинаковые события. Порядок действий,
ограничение очереди, ошибки и сохранность результата проверяются независимо от
числа файлов в секунду.
