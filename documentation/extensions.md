# Расширение движка

## Границы модулей

| Подсистема | Интерфейс | Ответственность |
| --- | --- | --- |
| Наблюдение | `include/fileward/watcher.h` | События ядра, подписки и покрытие |
| Планировщик | `include/fileward/runtime.h` | Ограниченная очередь, готовность, версии правил, потоки и метрики |
| Правила | `include/fileward/rules.h` | Общая проверка условий для run/test/explain |
| Исполнитель | `include/fileward/action.h` | Поиск обработчика, проверка вызова и исполнение |
| Состояние | `include/fileward/state.h` | Совместимый TSV успешно выполненных действий |
| Аудит | `include/fileward/audit.h` | Версионированный JSONL и отказ записи |
| Управление | `include/fileward/control.h` | Ограниченный локальный протокол и клиент |

Наблюдатель передаёт `file_event_t` через callback планировщику. Планировщик
владеет заданиями и неизменяемыми снимками конфигурации, исполнитель получает
только конкретное действие, путь, тип события и dry-run. Обработчик не управляет
очередью или жизненным циклом демона. Хранилище состояния владеет своей блокировкой;
JSONL остаётся отдельным основным аудитом.

## Модульные действия

`src/actions/registry.c` содержит единственный реестр имён и функций, общий для
парсера и исполнения. Команда `fileward actions` выводит зарегистрированные действия
и числовую маску возможностей. Сейчас это log, move, copy, archive, exec.

| Возможность | Маска | Синтаксис |
| --- | --- | --- |
| `ACTION_MESSAGE` | 1 | Необязательное сообщение |
| `ACTION_TARGET` | 2 | Один каталог назначения с шаблонами |
| `ACTION_COMMAND` | 4 | Команда с литеральным абсолютным исполняемым файлом |
| `ACTION_FILE_OPTIONS` | 8 | conflict/retries/backoff |
| `ACTION_TIMEOUT` | 16 | timeout |

Расширение происходит при сборке. Чтобы добавить действие:

1. Добавьте тип в `action_type_t` в `config.h` и функцию в отдельном `.c`.
2. Объявите функцию в `src/actions/handlers.h` и добавьте исходник в Meson.
3. Добавьте дескриптор в реестр: уникальные тип и имя, возможности, callback.
4. Используйте одно из существующих представлений аргумента в `action_t`.
   Новый формат аргументов требует явного расширения парсера и модели конфигурации.
5. Проверьте validate/test/explain, исполнение, ошибку, dry-run, отмену и параллельность;
   опишите поведение в русской документации.

Сигнатура callback:

```c
int handler(const action_t *action, const char *watch_root,
            const char *relative_path, event_type_t event, int dry_run);
```

Результат: 0 — исполнено; `ACTION_SKIPPED` — предусмотренный пропуск;
-1 — ошибка с установленным errno. Вызов может происходить одновременно из нескольких
рабочих потоков. Не используйте изменяемое глобальное состояние без синхронизации;
не удерживайте указатели на конфигурацию после возврата. Входной путь уже проверен
диспетчером как относительный, но обработчик отвечает за свои файловые операции,
симлинки, конфликты, таймауты и реакцию на отмену: `action_cancelled()` возвращает 1 и выставляет
`errno=ECANCELED`, если требуется остановка. Общие функции шаблонов выполняют
один проход подстановки без shell. В dry-run побочных эффектов быть не должно.

Планировщик сам создаёт action_started/action_result, измеряет длительность и
записывает успех в state-file. Специальные детали исполнения можно добавлять через
API аудита; рабочий поток уже имеет контекст исходного события и правила.

Это интерфейс модулей, собираемых вместе с программой. ABI для внешних `.so`,
динамическая регистрация и sandbox сторонних плагинов в 1.0 не предоставляются.

## Изменение состояния

`state_store_create/append/destroy` изолируют путь, формат TSV и сериализацию записи.
Отсутствующий путь отключает совместимый журнал. Симлинки, FIFO и другие специальные
файлы отклоняются без блокирующего открытия. Ошибка append превращается в
`FW_STATE_WRITE`; она не отменяет уже выполненную операцию. Для структурированной
истории используйте JSONL. Сохранения и воспроизведения очереди заданий этот модуль
не выполняет; изменение такого контракта потребует отдельного протокола восстановления.
